# Korean Train Stats website

This public repository, [Bttlbmb/korean-train-stats](https://github.com/Bttlbmb/korean-train-stats), holds the static site at <https://koreantrainstats.com/>. It has seven kinds of page:

- the front page (`index.html`), with yesterday and the past 30 days;
- a train page for each train that ran in the past 30 days (`train/<id>/`);
- the all-trains page (`trains/`), with a row for each of those trains, which the front page’s header links to;
- the all-stations page (`stations/`), with a row for each station where a train reported an arrival in the past month, which the front page’s header links to;
- a station page for each of those stations (`station/<id>/`), which the all-stations page links to;
- a day page for each complete day since collection began (`day/<date>/`);
- a month page for each complete calendar month (`<year>-<month>/`, such as `2026-10/`), which the backend writes and no page links to yet.

The pages are plain HTML, CSS, and JavaScript modules, with no framework. Their figures come from the JSON files in `data/`, which the backend’s exporter writes each night.

## Preview

```sh
python3 scripts/preview.py
```

The preview builds the site into `_site/`, which git ignores, and serves it at <http://127.0.0.1:8765/> on this machine only. It needs Node.js 18 or newer. Restart it to see a change.

The Korean version starts at <http://127.0.0.1:8765/ko/>. [The glossary](docs/korean.md) owns its wording, references, and review status.

## Build and publishing

`scripts/build.mjs` turns the data into finished HTML pages with the same modules the browser runs (`js/front.js`, `js/train.js`, `js/trains.js`, and `js/day.js`), so search engines and link previews read every page without running scripts. The build:

- copies the site’s files, leaving out hidden files, `artifacts/`, and the repository’s own guides and scripts;
- fills in both front pages and writes English and Korean train, train-list, all-stations, station, and day pages;
- keeps the exporter’s English month HTML and builds Korean month pages from the archived day files through `js/month.js`;
- adds language links, reciprocal `hreflang` annotations, and a sitemap containing both languages;
- stops on a rendering error, incomplete month archive, or unresolved Korean station name so a partial translation does not publish.

An address without a page returns `404.html`. A built train, day, or station page sits two folders down and the all-trains page one; each sets a `<base>` that points at the site root, so their links work like the front page’s; their skip link names their own address, because a bare `#main` would resolve to the front page. `app.html` only forwards old `app.html?train=<id>` and `app.html?day=<date>` links. The built files are never committed.

Push experiments to `main`. GitHub Actions checks them there. The daily job exports into `production`, whose own workflow builds and deploys the public site. A failed experiment on `main` leaves daily publishing independent.

To release a tested website change, start a separate checkout at the latest `origin/production`, cherry-pick the intended website code commits, then run the train check, build, and locale check against that checkout’s data. Push the tested commit with `git push origin HEAD:production`. If a daily update lands first, repeat from the new production tip. The backend replaces production history with one commit at each data refresh. Development history stays on `main`.

The domain is set in `CNAME`. Its DNS records are at Cloudflare and must stay “DNS only”: Cloudflare’s proxy stops GitHub from issuing the HTTPS certificate. GitHub redirects `https://bttlbmb.github.io/korean-train-stats/` to the domain.

The site makes no outside requests except to Google Fonts, which have local fallbacks.

## Data

`data/` holds the exporter’s output; never edit it by hand. The site reads `meta.json` (the complete-date range and any date still collecting), `days.json`, `windows/yesterday.json`, `windows/month.json`, `stations/index.json`, `trains/<id>.json`, and `days/<date>.json`. The backend’s `BUILD_NOTES.md` lists their fields and owns the definition of every figure. The exporter also writes `sitemap.xml` and the month folders at the site root.

## Interface

The backend’s `BUILD_NOTES.md` owns the metric definitions. “On time” always means within 5 minutes.

### Front page

`index.html` is the front page. The build fills it from `js/front.js`; when it loads, `js/start.js` draws it again from the data, so “yesterday” stays true on a day without an update, and makes the dots and bars interactive. Its header holds the site name and two outlined buttons, “All trains” and “All stations”, to the all-trains and all-stations pages; the language switch sits beside them, and on phones the buttons drop to their own row below the site name and the switch, each taking half of it. It reads `meta.json`, `days.json`, and the two window files.

- It has one row for Yesterday and one for the past 30 days. Each row has a 64-pixel share of stops within 5 minutes, one sentence, support lines (the typical delay when late, and for the 30 days the best and worst days), and a visual of the same height.
- **Yesterday** draws one dot per train in order of departure: late color when the train had a reported stop more than 5 minutes late, grey when it had no countable stops. Hover and the arrow keys name a train. A click, or Enter on a selected dot, opens its page; on touch screens the first tap selects a dot and a second tap opens it. A screen-reader table lists the trains with a late stop.
- **Past 30 days** draws one bar per calendar day on a true 0–100% axis, in one green on a late-orange track by that day’s share within 5 minutes (a legend under the bars names both), and a short outlined stub for a day not collected. Hover, touch, and the arrow keys show a day’s share and late stops, and the bars open their day page the same way the dots open train pages. Each bar with data is a real `<a href="day/<date>/">`, so search engines follow it and a middle-click opens a new tab; the links stay out of the tab order, so the chart is one keyboard stop. With fewer than 30 complete days, the sentence says “the N days collected so far.”
- The page says “yesterday” and “past 30 days” only when the newest complete date is yesterday in Korea time. Otherwise it names the dates, such as “the 30 days to 24 Oct.”

### Train page

`train/<id>/` is built from `js/train.js`; `js/app.js` adds the tooltips and the day strip. The header holds the site name, linking to the front page in the current language, and a language switch. The page always covers the past month.

- **Heading:** a back button to the front page, the title, a meta line (the scheduled departure and arrival times, the number of stops, and the date range), and a stats line: the share of stops within 5 min, the days on time at the final stop, and the typical delay when late, which is left out for a train with no late arrival (130 trains now). A train with fewer than 10 recorded days has a muted line under them saying why the train and station lists show no share for it; its own figures stay, since the page shows the days behind them. On phones the route is a subtitle on its own line under the train, smaller and in grey, breaking before an arrow and never after it, and the lines under the title use the full width, below the back button; the day, month, and all-trains pages share that layout. A small grey map of South Korea with the route in ink sits to the right, drawn from the station coordinates and the outline in `js/korea.js`. It is decoration, so screen readers skip it, and it is left out unless every stop has coordinates.
- **Stop list:** titled “Delay at every stop in the past 30 days”, with one row per stop. Each row shows the scheduled arrival at the left (at the origin, the departure, marked “departs”, and a small +1 after midnight), one dot per recorded day at its delay in whole minutes (green within 5 minutes, orange later, with a dashed line between 5 and 6 minutes), and the share of days within 5 minutes at the right, or a dash when no arrival was reported. The origin has no arrival delay, so it has no dots and no share; its row carries the small “5 min” and “within 5 min” labels instead. Stop names link to their station pages (see the station-page decision). On phones the “departs” mark is hidden and the time column narrows. At 360 pixels and below the card padding and columns tighten so no stop name touches a dot, and the “5 min” label sits to the left of its line. The axis runs from −2 minutes to the 97th percentile of the train’s delays rounded up to 5 (never below 15); a day later than its end is drawn at the track’s end as a dot with a small arrow pointing out (the `.out` dots: one stack of up to 5 arrows 5.5 pixels apart at every width, extra columns stepping inward 12 pixels), the legend then adds “Later than N min”, and the row’s tooltip adds the longest delay. A day earlier than −2 minutes stays a plain dot at the start, because it is always within 5 minutes. The track ends 6 pixels before the share figure so an arrow keeps clear of it. Days with the same delay stack in a grid. In the browser, `packRailDots` in `js/app.js` lays the dots out again with the track’s real width, and again when it changes: a stack keeps its minute unless a neighbor needs the room, no dot crosses the dashed line or leaves the track (the arrow dots keep their place at its end and the others keep clear of them), tracks under 260 pixels use a tighter grid, and tracks under 100 pixels also use 3.8 pixel dots. Without JavaScript the built layout stays.
- **Day by day:** one cell per calendar day across the card, colored by the delay at the final stop, with a mark for a timetable change. It keeps calendar gaps, and its tooltips tell a day not collected from a day without a run and from an unavailable or missing record. The strip is one tab stop: the arrow keys step through the days and show each tooltip, and Escape clears it. A legend names the colors, with “No data” for a day without a value; on phones it is a grid of three columns. A screen-reader table lists every day.

### Day page

`day/<date>/` is built from `js/day.js` and has the train page’s header.

- **Heading:** a back button, the date as the title (the day, month, and year stay together on one line), a meta line (trains and stops), and three figures: stops within 5 min, trains with a late stop, and typical delay when late. A train counts when it has a countable arrival.
- **How late stops were:** one bar split into within 5 min, 6–10, 11–20, 21–30, and over 30 minutes, sized by stops, so its green share is the heading’s figure. A legend under the bar names every part with its share, hover gives its stop count, and a screen-reader table lists them. On phones the legend has two columns with the shares aligned at the right.
- **Biggest delays:** up to 10 trains with the largest delay at any stop, only those more than 5 minutes late. Each row has the train, its route with scheduled departure and arrival times, the stop with the largest delay, the scheduled and reported arrival there, and the delay with a dot in its color. Korail reports a delay but no observed arrival time, so the reported arrival is the scheduled one plus the delay. A train links to its page only while it has one, so an older day lists some trains without a link. Under 760 pixels the route and stop columns are hidden and shown as a small line under the train, such as “Seoul → Busan · at Busan”, and the other cells align with the train line. On the day and month pages that line is 12 pixels, “at Busan” moves as a unit and drops the dot before it when it starts a new line, and the whole row opens the train (on the month page the date link still opens its day page); the day page also hides the reported arrival column, because the delay already gives it. A day with no late stop says so instead of showing a table.

### All-trains page

`trains/` is built from `js/trains.js`; `js/app.js` loads `js/trains-page.js` to add the controls. It has the train and day pages’ header: the back button to the front page, the title, a line with the number of trains and the data period, and a line with the overall share of stops within 5 minutes and the number of trains within 5 minutes at every stop.

- **Most punctual and Least punctual** list five trains each, from the trains with at least 20 recorded days, with the route and the share within 5 minutes with a bar. A tie goes to the train with more counted stops. On phones each list shows three trains.
- **Find a train** holds the type boxes (KTX, ITX with its three services combined, Mugunghwa, and Other), the Starts at and Ends at dropdowns, a Reset link, the share legend, and the table. A dropdown offers only the stations that still lead to a train, given the ticked types and the other station. The two dropdowns match a train’s first and last station, not its middle stops; the owner renamed them from From and To on 13 November 2026 so they do not promise a journey search. The address keys stay `from` and `to`.
- **The table** has one row for each train with a page: train, route, departure, arrival (with +1 after midnight), and share within 5 minutes with a bar in the share colors. A share needs 10 recorded days; otherwise the row shows only a dash, with no bar, and sorts last. The table shows its first 40 trains, then a “Show all N trains” button that shows the rest and moves focus to the first new row (`data-cap` on the table body, set from `ROW_CAP` in `js/utils.js` and read by `js/trains-page.js`); every row is in the built page, filters and sorting work on all of them, the cap applies to what they leave, and Reset restores it. A click on a header sorts and a second click reverses; phones have a Sort by dropdown instead, show each train on two lines (the name and share, then the route and times), and lay the type boxes out as a grid of two columns with From and To side by side. At 360 pixels and below the times join the name and the route keeps the second line. The whole row links to the train page, and the header stays at the top while the table scrolls.
- **The address** keeps the choices, such as `?types=KTX,ITX&from=Busan&to=Seoul&sort=dep_asc`, so a shared link restores them. The page writes it with `replaceState`, so Back leaves the page. The controls need JavaScript and stay hidden without it; the lists and the whole table, links included, are in the HTML.

### All-stations page

`stations/` is built from `js/stations.js`; `js/app.js` loads `js/trains-page.js` to add the controls. It has the train and station pages’ header: the back button to the front page, “All stations”, a line with the number of stations and the data period, and a line with the share of all stops within 5 min.

- **Busiest and Least punctual** list five stations each. Busiest ranks by the number of trains that call there. Least punctual ranks by the lowest share within 5 min among stations with at least 200 reported stops, and a tie goes to the station with more stops. Each row shows the train count and the share with a bar; the Busiest card's header names both (“Trains that call · stops within 5 min”), since its bars are not what it ranks by; on phones each list shows three stations. The lists are left out when fewer than five stations have 200 stops.
- **Find a station** holds a name search (it matches the English and the Korean name, and the placeholder is English on the English page), the type boxes for the train types that call at a station (KTX, ITX with its services combined, Mugunghwa, and Other; a station stays when any ticked type calls there), a Reset link, the share legend (“Share of stops within 5 min”), and the table.
- **The table** has one row for each station: name (a link to its page), the train types, the number of trains, and the share within 5 min with a bar. A share needs 10 reported stops; otherwise the row shows only a dash. It starts in name order, the Station, Trains, and Share headings sort it (Trains and Share start with the highest), and the first 40 stations show before a “Show all N stations” button, as on the trains pages.
- **The address** keeps the choices, such as `?q=dae&types=KTX&sort=num_desc`, so a shared link restores them. Enter in the search box does not submit the form. The controls need JavaScript and stay hidden without it; the lists and the full table are in the page.

### Station page

`station/<id>/` is built from `js/station.js`; `js/app.js` loads `js/trains-page.js` to add the controls. The station ID is the one in `stations/index.json`. A station gets a page when a train reported an arrival there in the past month. It has the train page’s header: the back button, “<Station> station” (Korean: the name and 역), a line with the number of trains that stop there, how many start there (a loop train counts once), and the number of reported stops with the data period, and a stats line with the share of stops within 5 min and the figure for each train type that stops there (KTX, ITX with its services combined, Mugunghwa; Other is left out of the breakdown but counted in the total, and the breakdown is left out when only one type calls). The map is the train page’s, with a pin and a faint ring instead of a route, and is left out when the station has no coordinates or on phones.

- **Calls, not trains:** a row is one call of one train, from the train’s current timetable, so a train that calls twice (Hongseong on the ITX-Maum loop) has two rows, though the header, the description, the type boxes and the all-stations count count it once; where rows outnumber trains the table count says “stops” (Hongseong: 47 trains, 53 stops). A reported arrival counts at the stop it was reported for, matched across timetable versions by station and visit; an arrival at a stop the current timetable no longer has is left out, as on the train page. A train that starts at the station has a time marked “departs”, no arrival, and a dash; one that ends there says “Ends here” under Toward.
- **Most punctual and Least punctual** list up to five trains each, from the calls with at least 20 reported stops, with the arrival time, the route, and the share within 5 min with a bar. A train is never in both lists, so each list has at most half the ranked trains and the lists are left out below four. A tie goes to the call with more reported arrivals, then the train ID; many trains tie at 100%, so the note under Most punctual says how many were within 5 min on every recorded day.
- **Find a train at <station>** holds the type boxes (left out when one type calls), a Toward dropdown, a Reset link, the share legend (“Share of stops within 5 min”), and a table with arrival time, train, Toward (the train’s last stop), and share within 5 min with a bar. A share needs 10 reported stops; otherwise the row shows only a dash, with no bar. The table starts in order of arrival time, so trains after midnight come last, and the headers sort it. On phones each row is two lines, with the time first.
- **Long and short tables:** the table shows its first 40 trains, then a “Show all N trains” button that shows the rest and moves focus to the first new row (`data-cap` on the table body, the same cap as on the all-trains page). Every row is in the built page, so search engines and readers without JavaScript get all of them, and filters and sorting work on every row; the cap applies to what they leave, and Reset restores it. A station with 10 trains or fewer has no controls, no count line, and plain column headings, only the legend and the table, and loads no script.
- **The address** keeps the choices, such as `?types=KTX&to=Busan&sort=share_asc`. The controls need JavaScript and stay hidden without it; the lists and the full table are in the page.

### Search and link previews

- Each page has its own title, description, and canonical link. Train, day, station, all-stations, and all-trains pages take them from `pageInfo` in `js/train.js`, `js/day.js`, `js/station.js`, `js/stations.js`, and `js/trains.js`; the exporter writes the month pages’ into their markup. The front-page title is the question the site answers, “Korean Train Stats: How punctual are South Korea’s trains?”; its description names KTX and Korail, the words people search for, because the site’s name has neither. Inner titles put what tells pages apart first, since a tab shows only the first words: “Tuesday, 8 September 2026: Korail train delays” for a day, “October 2026: Korail train punctuality” for a month, and “KTX 456 Mokpo → Seoul delays” for a train. A description carries the page’s main figure.
- `sitemap.xml`, expanded to both languages by the site build from the exporter’s records, lists the front page, the all-trains page, the all-stations page, and every train, station, day, and month page; `robots.txt` allows everything and names it. Submit `https://koreantrainstats.com/sitemap.xml` once in Google Search Console and Bing Webmaster Tools.
- The front page and each month page describe the data as a schema.org Dataset in JSON-LD, for Google Dataset Search.
- Every page has link-preview tags (Open Graph and a large `twitter:card`) and the one site image, `og.png` (1,200 by 630 pixels: the logo, the site name, and “How punctual are South Korea’s trains?”). The image carries no figure because messengers keep a preview for days, so a figure would go stale.

### Colors, legends, and type

- `tokens.css` holds the Porcelain palette: nearly neutral greys, an ink-navy accent, and a muted terracotta delay ramp. Green means on time, the warm ramp means late, grey is neutral, and the accent marks links, hover, and focus only. Cells use `--ontime`, dots the darker `--ontime-mark`; share bars use one green in four steps (`--ontime-dark` for 90% or more, `--ontime-mark` 80–89%, `--ontime-mid` 70–79%, `--ontime` under 70%, from `SHARE_BANDS` in `js/utils.js`); headline figures use `--ink`. `theme-color` repeats the canvas color.
- Every color scale has a legend that names what it measures and labels each step. The share legend reads Within 5 min and More than 5 min late (Korean 5분 이내 and 5분 넘게 늦음), and on phones its label sits on its own line. A card whose heading already names the measure, such as the month page’s day by day bars, leaves the label out.
- On phones the back button and the site name have 44 pixel tap areas that extend beyond how they look, and the site name drops to 18 pixels at 360 pixels and below so it stays on one line.
- Names that link (trains, stations, and the dates in the month table) are in the text color in tables and lists and never underlined, at rest or on hover; a row's tint shows the hover. Navy is for links inside running text and for keyboard focus. Header buttons, the language switch, type boxes, dropdowns, the search box and the Show all button are 36 pixels tall on desktop and 44 on phones. The Reset link beside a table's count is text on the count's line, so it adds no height when it appears; an invisible margin gives it a 44 pixel tap area. The site has one font family, IBM Plex Sans (the Korean pages add IBM Plex Sans KR); the body turns on tabular numerals, so the digits of times and shares line up in columns. The owner chose on 12 November 2026 to drop the monospace font, which had set times and shares apart from the text beside them.
- The back arrow links to the front page and its label and tooltip read “Back to front page” (Korean 처음으로); the exporter writes the same label on the month page. In the browser, `js/app.js` makes it go back one step instead (label “Back to previous page”, Korean 이전 페이지로) when the reader came from another page of this site in the same language, which keeps the filters and scroll position of the page they left. It stays a link to the front page for a search or bookmark visit, a language switch, a page opened in a new tab, a modifier-key click, and without JavaScript. A reload reports the page as its own referrer, so the decision is kept in the history entry's state. The owner chose this on 12 November 2026, after stop names became links and the arrow dropped readers on the front page from a station page.
- The back button’s top margin follows the heading size (`--h1-size`: 26 pixels, 23 at 560 pixels and below), so it stays centered on the title’s capitals; a fixed margin hung low at the phone size.
- No text is smaller than 12 pixels. Card titles are H2 headings.

## Checks

- After a build, run `node scripts/check_locales.mjs`. It checks every language pair, internal target, canonical address, language annotation, and sitemap entry, plus matching chart figures and calendar-month edge cases. Publishing runs both renderer and language checks before uploading.

- Run `node scripts/check_trains.mjs` after changing a page’s renderer or refreshing `data/`. It renders every train, day, station, all-stations, and all-trains page and fails on an error, text such as “undefined” or “NaN”, a final stop whose dots do not match the heading’s count, a row whose share does not match its dots, or a missing or overlong title and description. For a day page it also fails when the delay buckets do not add up to the stops, or the stops or share differ from `days.json`. For the all-trains page it fails when a train page has no row or a train appears twice, or when a row’s share differs from its train file. For a station page it fails when a table row does not link to its train or shows a share that its figures do not give, and when the arrivals on all station pages differ from the arrivals in the train files. For the all-stations page it fails when a station page has no row or a station appears twice, or when a row’s share differs from its figures.
- Run `node scripts/build.mjs` after changing any page.
- In the preview, check the front page, the all-trains page, the all-stations page, a train page, a station page, and a day page at 360, 768, 1,280, and 1,440 pixels: the dot and bar click-through, the filters, sorting, and Reset with their address, Back, the empty, error, and missing-data states, and that no request fails. Wide content scrolls inside its own container, never the page.
